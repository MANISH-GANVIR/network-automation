API FLOW & COMMUNICATION LAYERS
=========================================
"Sir, when the user clicks a button on the UI, like reset or discovery, it triggers a function in the frontend, specifically in app.js.

From there, the DOM API reads the input values, such as peer IP or firewall selection. Then the Fetch API sends an HTTP POST request to the backend, for example /asa/reset.

On the backend side, FastAPI receives this request in main.py and forwards it to the middleware, which is web_wrapper.py.

The middleware is responsible for routing the request to the correct operation. It first establishes a connection to the firewall using Netmiko and performs a discovery to get the current tunnel information.

Based on the task, for example reset, it calls the appropriate function from the automation layer, like reset.py.

That function executes the required CLI command, such as vpn-sessiondb logoff tunnel-group, through Netmiko over SSH.

The firewall processes the command and returns the output, which is captured by the backend.

Then the backend formats this output into a JSON response and sends it back to the frontend.

Finally, the Fetch API receives the response, and the DOM API updates the UI to display the output in a terminal-like view.

So overall, the flow is: frontend sends a request, backend processes it, Netmiko executes commands on the firewall, and the response is displayed back on the UI."

Q3) How does frontend-backend communication work?
──────────────────────────────────────────────────
Answer:
Frontend (app.js) uses the Fetch API to send asynchronous HTTP POST
requests to backend REST API endpoints.

Example (app.js):
fetch(`http://127.0.0.1:8000/api/asa/reset`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ username, project, firewall })
})
.then(response => response.json())
.then(data => {
    document.getElementById("asaOutput").innerText = data.output;
})

The backend (FastAPI in main.py) receives the request at endpoint
/api/asa/{task}, processes it through the middleware layer, executes
the automation logic, and sends back a JSON response. The frontend then
uses DOM API to update the UI with the response data.


Q4) What is the role of middleware?
───────────────────────────────────
Answer:
Middleware (web_wrapper.py) acts as a router between the FastAPI server
and the automation layer.

Role:
  • Receives request from FastAPI with task parameter
  • Decides which automation function to call based on task
  • Routes request to appropriate function (build_vpn, reset_vpn, etc.)
  • Returns response back to FastAPI

Example:
def run_web(task, payload):
    if task == "reset":
        return reset_vpn(conn, payload)
    elif task == "build":
        return build_vpn(conn, payload)
    elif task == "update":
        return update_vpn(conn, payload)

This decouples FastAPI from business logic, making the code modular and
maintainable.


Q5) What is Netmiko and how does it work?
───────────────────────────────────────────
Answer:
Netmiko is a Python library for SSH communication with network devices.

Role:
  • Establishes SSH connection to firewall (Cisco ASA, Palo Alto)
  • Sends CLI commands to the device
  • Captures and returns command output
  • Handles SSH authentication and session management

Example (client.py):
from netmiko import ConnectHandler

conn = ConnectHandler(
    device_type='cisco_asa',
    host='192.168.1.1',
    username='admin',
    password='password'
)

# Execute command
output = conn.send_command("show crypto ikev1 sa")

# Send configuration
conn.send_config_set(["config t", "crypto ikev1 policy 1", ...])

Netmiko abstracts SSH complexity and provides simple methods to interact
with network devices, making automation easier.

from netmiko import ConnectHandler
def main():
    try:
        # Device details stored in a dictionary
        asa = {
            "device_type": "cisco_asa",  # Type of network device
            "host": "192.168.1.1",  # IP address of ASA firewall
            "username": "admin",  # Login username
            "password": "admin123",  # Login password
            "secret": "enable123"  # Enable mode password
        }

        # Establish SSH connection using Netmiko
        # ConnectHandler creates the connection
        # **asa unpacks dictionary into arguments
        conn = ConnectHandler(**asa)

        # Enter enable (privileged) mode
        conn.enable()

        # Execute command on device
        output = conn.send_command("show run")

        # Print the output
        print(output)

        # Close the connection
        conn.disconnect()

    except Exception as e:
        print("Error:", e)
    finally:
        print("\n\n Test completed. Ensure ASA is reachable and credentials are correct.")

# 🔥 main call
if __name__ == "__main__":
    main()

        conn = ConnectHandler(**pa)

        # Run command
        output = conn.send_command("show system info")
        print(output)

        # Disconnect
        conn.disconnect()

    except Exception as e:
        print("Error:", e)

    finally:
        print("\nTest completed.")


if __name__ == "__main__":
    main()

"""
Palo Alto Firewall Policy Automation Script
Deploys security rules from CSV file to Palo Alto firewall
"""

# Import login function from login.py module
from login import login

# panos = Palo Alto Networks Python SDK
# firewall module = Contains Firewall class to connect and manage Palo Alto firewalls
# policies module = Contains SecurityRule and Rulebase classes to define firewall rules
from panos import firewall
from panos import policies

# csv = Built-in Python module to read/write CSV (Comma-Separated Values) files
# Used here to read firewall rules from Excel/CSV format
import csv

def main():
    """
    Main function - Orchestrates firewall rule deployment
    """
    try:
        # 🔥 Call login function to get firewall credentials
        hostname, username, password = login()

        # Connect to Palo Alto firewall using credentials
        # firewall.Firewall() = Class from panos library that establishes connection to firewall
        fw = firewall.Firewall(hostname=hostname, username=username, password=password)
        print(f"Connected to Firewall {hostname}")

        # Create a new rulebase object
        # Rulebase = Container that holds all security rules for the firewall
        rule_base = policies.Rulebase()

        # Add rulebase to firewall object
        # This registers the rulebase with the firewall instance
        fw.add(rule_base)

        # Initialize empty list to store rules
        rule_list = []

        # Define path to CSV file containing firewall rules
        # r = Raw string (treats backslashes as literal characters, not escape sequences)
        # Example: r"D:\rules_csv.csv" means literal backslashes, not escape characters
        # Without r: D:\rules_csv.csv would try to interpret \r as carriage return
        csv_path = r"D:\rules_csv.csv"

        # Open and read CSV file
        # open() = Built-in Python function to open files
        csv_open = open(csv_path)

        # csv.reader() = Parses CSV file and converts each row into a list
        # Example: "Allow_HTTP,trust,192.168.1.0" becomes ["Allow_HTTP", "trust", "192.168.1.0"]
        csv_read = csv.reader(csv_open)

        # Loop through each row in CSV file
        for row in csv_read:
            # Create SecurityRule object for each row from CSV data
            # SecurityRule = Class from panos.policies that defines a firewall security rule
            # CSV format: name | fromzone | source | tozone | destination | service | application | action
            rule = policies.SecurityRule(
                name=row[0],                          # Rule name (e.g., "Allow_HTTP")
                fromzone=row[1].split(" "),           # Source zone - split by space into list
                                                      # Example: "trust untrust" becomes ["trust", "untrust"]
                source=row[2].split(" "),             # Source IP/network - split by space into list
                                                      # Example: "192.168.1.0 192.168.2.0" becomes ["192.168.1.0", "192.168.2.0"]
                tozone=row[3].split(" "),             # Destination zone - split by space into list
                destination=row[4].split(" "),        # Destination IP/network - split by space into list
                service=row[5].split(" "),            # Service/Port - split by space into list
                                                      # Example: "service-http service-https" becomes ["service-http", "service-https"]
                application=row[6].split(" "),        # Application type - split by space into list
                action=row[7]                         # Action - allow/deny/etc
            )

            # Add rule to rule_list
            # This stores the rule in memory before deploying to firewall
            rule_list.append(rule)
            print(f"Prepared Rule: {row}")

        # Loop through all prepared rules and deploy to firewall
        for rule in rule_list:
            # Add rule to rulebase
            # This associates the rule with the rulebase object
            rule_base.add(rule)

            # Create rule on firewall (API call)
            # rule.create() = Sends API request to Palo Alto firewall to create this specific rule
            rule.create()
            print(f"Created Rule: {rule.name}")

        # Commit all changes to firewall (save configuration)
        # fw.commit() = Saves all changes to firewall's permanent configuration
        # Without commit(), rules would be created but not saved - they'd be lost on reboot
        fw.commit()
        print("Commit successful")

        # Close CSV file
        # Important to close file after reading to free up system resources
        csv_open.close()

    except Exception as e:
        # Catch and print any errors that occur
        # Exception = Any error (file not found, connection failed, invalid data, etc.)
        print(f"Error: {e}")

if __name__ == "__main__":
    # Entry point - run main function
    # This ensures main() only runs when script is executed directly
    # (not when imported as a module in another script)
    main()

ANSWER (Short & Interview-Ready):SSH libraries with different abstraction levels.

"Sir, these are three SSH libraries with different abstraction levels.

PARAMIKO - Lowest level
- Pure SSH connection library
- Need to write a lot of code manually
- Full control but complex
- Use case: When you need custom SSH workflows

NETMIKO - Medium level (Built on Paramiko)
- Simplified for network devices
- Supports 50+ device types (Cisco, Juniper, etc.)
- Just specify device type and send commands
- Use case: CLI-based configuration (80% of my work)

NAPALM - Highest level (Multi-vendor)
- Same code works on ANY vendor device
- Write once, run on Cisco/Juniper/Arista/Palo Alto
- More abstract, less control
- Use case: Multi-vendor environments


SIMPLE COMPARISON:
-----------------
Paramiko:   Low abstraction, high control, complex code
Netmiko:    Medium abstraction, easy to use, vendor-specific
NAPALM:     High abstraction, simplest code, multi-vendor

ABSTRACTION = How much complexity is hidden from you

More Abstraction = Easier to use = Less control = Less code
Less Abstraction = Harder to use = More control = More code

Choose based on your needs:
- Need full control? → Use LOW abstraction (Paramiko)
- Need simplicity + control? → Use MEDIUM abstraction (Netmiko)
- Need multi-vendor support? → Use HIGH abstraction (NAPALM)

WHAT IS THREADING? (Simple Explanation)
================================================================================

THREADING = Running multiple tasks at the SAME TIME

NOT one after another, but ALL TOGETHER at the same time.


REAL LIFE EXAMPLE:
==================

WASHING CLOTHES WITHOUT THREADING:
1. Wash shirt (30 min)
2. Wait for shirt to finish
3. Wash pants (30 min)
4. Wait for pants to finish
5. Wash socks (30 min)
Total: 90 minutes (one after another)


WASHING CLOTHES WITH THREADING:
1. Put shirt in washing machine
2. Put pants in washing machine
3. Put socks in washing machine
4. ALL THREE WASH AT THE SAME TIME
Total: 30 minutes (all together)

Result: 90 min → 30 min (3x faster!) ⚡


ANOTHER EXAMPLE:
================

COOKING WITHOUT THREADING:
1. Cook rice (10 min)
2. Wait for rice to finish
3. Cook dal (10 min)
4. Wait for dal to finish
5. Cook vegetables (10 min)
Total: 30 minutes


COOKING WITH THREADING:
1. Start rice cooking
2. Start dal cooking (at same time)
3. Start vegetables cooking (at same time)
4. All cook together while you wait
Total: 10 minutes (all at same time)

Result: 30 min → 10 min (3x faster!) ⚡


CISCO SWITCH EXAMPLE:
====================

CONFIGURING SWITCHES WITHOUT THREADING:

Switch 1: Connect → Configure → Disconnect (4 minutes)
Switch 2: Connect → Configure → Disconnect (4 minutes)
Switch 3: Connect → Configure → Disconnect (4 minutes)
Switch 4: Connect → Configure → Disconnect (4 minutes)
Switch 5: Connect → Configure → Disconnect (4 minutes)

Total: 4 + 4 + 4 + 4 + 4 = 20 minutes (one after another)


CONFIGURING SWITCHES WITH THREADING:

Switch 1: Connect → Configure → Disconnect
Switch 2: Connect → Configure → Disconnect     } All at same time
Switch 3: Connect → Configure → Disconnect
Switch 4: Connect → Configure → Disconnect
Switch 5: Connect → Configure → Disconnect

Total: 4 minutes (all happening together)

Result: 20 min → 4 min (5x faster!) ⚡


VISUAL COMPARISON:
==================

WITHOUT THREADING (Sequential):
|----Switch 1----|----Switch 2----|----Switch 3----|----Switch 4----|----Switch 5----|
0               4               8               12              16              20 min

WITH THREADING (Parallel):
|----Switch 1----|
|----Switch 2----|
|----Switch 3----|  All happening together
|----Switch 4----|
|----Switch 5----|
0               4 min


KEY POINT:
===========

Threading = Do multiple things at the same time
Not threading = Do one thing, finish, then do next thing


PYTHON CODE EXAMPLE:
====================

WITHOUT THREADING:
```python
for device in devices:
    configure_device(device)  # Wait for this to finish
    # Then do next device

# THREADING LOOP WITH DETAILED COMMENTS

for device in devices:
    # Step 1: Create a thread for this device
    # threading.Thread() = Creates a new thread
    # target = Which function to run (configure_device function)
    # args = Arguments to pass to that function (the device info)

    thread = threading.Thread(target=configure_device, args=(device,))

    # Step 2: Start the thread
    # thread.start() = Run the function in this thread (in background)
    # Important: We DON'T wait for this thread to finish
    # We immediately move to the next device and create another thread

    thread.start()  # Don't wait, start next device too

    # Step 3: Add this thread to our list
    # threads.append(thread) = Store the thread in a list
    # We need to keep track of all threads so we can wait for them later

    threads.append(thread)

    # Step 4: Check if we have 5 threads running
    # if len(threads) == 5 = If we have created 5 threads
    # Then we should WAIT for all 5 to finish before creating more

    if len(threads) == 5:
        # Step 5: Wait for all 5 threads to complete
        # for t in threads = Loop through all 5 threads

        for t in threads:
            # t.join() = Wait for this thread to finish
            # join() means "don't move forward until this thread is done"
            # So we wait for all 5 threads to finish their configuration
            t.join()  # Now wait for 5 to finish

        # Step 6: Reset the threads list
        # threads = [] = Clear the list
        # Now the list is empty and ready for the next 5 threads
        # This way we can start 5 more threads without waiting for all 50
        threads = []


# EXAMPLE WITH ACTUAL NUMBERS:
# If we have 50 devices and use 5 threads:

# Iteration 1-5:
#   Create threads for Device 1, 2, 3, 4, 5
#   Start all 5 threads (they run together)
#   threads.append() adds them to list
#   List has 5 threads → condition is TRUE
#   Wait for all 5 to finish (takes 4 minutes)
#   Reset threads list to []

# Iteration 6-10:
#   Create threads for Device 6, 7, 8, 9, 10
#   Start all 5 threads (they run together)
#   threads.append() adds them to list
#   List has 5 threads → condition is TRUE
#   Wait for all 5 to finish (takes 4 minutes)
#   Reset threads list to []

# Iteration 11-15:
#   [Same pattern continues...]

# Total: 50 devices ÷ 5 threads = 10 batches × 4 min each = 40 minutes


# WHAT HAPPENS STEP BY STEP:
# ===========================

# Device 1: thread.start() → Starts in background (Don't wait!)
# Device 2: thread.start() → Starts in background (Don't wait!)
# Device 3: thread.start() → Starts in background (Don't wait!)
# Device 4: thread.start() → Starts in background (Don't wait!)
# Device 5: thread.start() → Starts in background (Don't wait!)
# List length = 5 → NOW WAIT
# thread.join() → Wait for Device 1 to finish ✓
# thread.join() → Wait for Device 2 to finish ✓
# thread.join() → Wait for Device 3 to finish ✓
# thread.join() → Wait for Device 4 to finish ✓
# thread.join() → Wait for Device 5 to finish ✓
# threads = [] → Clear list, ready for next batch
# [Continue with devices 6-10...]


# WHY DO WE DO THIS?
# ==================

# Without threading:
# Device 1 takes 4 min, then Device 2 takes 4 min = 8 min for 2 devices
# Slow! ❌

# With threading:
# Device 1 and 2 run together = 4 min for 2 devices
# Fast! ✓

# This loop ensures:
# ✓ 5 devices run at the same time (parallel)
# ✓ We don't start all 50 at once (would overload server)
# ✓ After 5 finish, we start 5 more
# ✓ Balanced performance and speed

Q4: WHAT IS REST API IN NETWORKING?
================================================================================

Sir, REST API is a way to interact with network devices using HTTP methods
instead of traditional SSH-based CLI access.

Traditionally, in networking we use SSH to connect to devices, execute commands,
and then parse the output. This process is more manual and less efficient,
especially when we scale automation.

For example, in SSH-based automation:
1. Connect to the device
2. Run commands like 'show version' or 'show route'
3. Read and parse the output manually

In my project, I worked on Cisco ASA firewall automation where I used Netmiko
to establish SSH connections, execute commands like 'show route' and
'show interface', and extract required information. This approach works,
but involves CLI parsing which adds complexity.

REST API provides a more structured and efficient way.

Instead of SSH, we send HTTP requests like GET, POST, PUT, DELETE, and the
device responds with structured data like JSON or XML.

For example, to get device information:
We simply send a GET request, and the response comes in JSON format,
which is already structured and easy to process.

In my project, I used both approaches based on device capability.

For Cisco ASA:
It has limited or no proper REST API support, so I used CLI-based automation
over SSH using Netmiko.

For Palo Alto firewalls:
They provide strong support for XML and REST APIs, so I used API-based automation.

For example, to create or update firewall configuration:
I send a POST request with parameters like source, destination, application,
and action.
The firewall processes the request and returns a success or failure response.

Benefits of REST API:
- Structured data (JSON/XML)
- No need to parse CLI output
- Faster and more automation-friendly

Real-world example:
Modern devices like Cisco Nexus switches and Palo Alto firewalls support REST APIs
and are widely used for scalable automation.

However, REST API depends on device support, so we must first verify whether
the device supports API or not.

So overall, REST API makes network automation more efficient, scalable, and
reliable, while traditional devices like Cisco ASA are mostly handled using
CLI-based automation.

Q7: WHAT IS VLAN AND VXLAN?
================================================================================

INTERVIEWER: "What is VLAN? How does it work? What about VXLAN?"

YOUR ANSWER:
============

"Sir, VLAN is basically logical division of a network.

VLAN EXPLANATION:
=================

Simple analogy - suppose a building has 4 floors. Physical cables from all
floors go to the switch. Create VLANs and you get:

Floor 1 = VLAN 100
Floor 2 = VLAN 200
Floor 3 = VLAN 300
Floor 4 = VLAN 400

Now Floor 1's broadcast traffic will not reach Floor 2! Completely isolated.

I used VLANs a lot in production.

Security example - I created VLAN 100 for the HR department and VLAN 200 for
the IT department. Now HR's sensitive salary data is not visible to IT! Good
security!

Performance also improves. If everything was in one VLAN, broadcast traffic
affects everyone. Separate VLANs limit broadcast traffic.

Flexibility - an employee transferred from Floor 1 to Floor 2. In the switch,
I just changed the port from VLAN 100 to VLAN 200. Never had to unplug or
replug! Beautiful!

To assign VLAN to an interface:

interface Ethernet1/1
switchport access vlan 100

Now this port is in VLAN 100.

I had a practical issue to solve - an employee accidentally got access to the
production server because of VLAN configuration. Risky!

I moved the employee's laptop from VLAN 100 (production) to VLAN 200
(non-production). Now they cannot access production data.

VLAN naming convention is important - the name should tell you what the VLAN
is for.


VXLAN EXPLANATION:
==================

Now sir, VXLAN is the modern evolution of VLAN.

VLAN has a limitation - it works only locally in one location. Can't extend
across cities or data centers.

Example: Company has 2 offices - New York and Los Angeles.

With VLAN:
- Create VLAN 100 in NY office
- Create VLAN 100 in LA office
- But they are separate!
- NY devices can't talk to LA devices
- Need routing = complex!

With VXLAN:
- Create VXLAN 100 in NY office
- Create VXLAN 100 in LA office
- They ARE connected!
- NY devices CAN talk to LA devices
- No routing needed = simple!

How VXLAN works?

VXLAN wraps the VLAN packet inside an IP packet (tunneling).

Simple VLAN packet → Can't travel over internet
Wrapped in IP packet → Can travel anywhere!

At destination, unwrap and device gets the VLAN packet.

Visual:

WITHOUT VXLAN:
NY Device → VLAN packet → BLOCKED AT INTERNET ✗
LA Device unreachable!

WITH VXLAN:
NY Device → VLAN packet → Wrap in IP → Travel internet → Unwrap → LA Device ✓
LA Device reachable!


VLAN VS VXLAN COMPARISON:
=========================

Feature              | VLAN           | VXLAN
---------------------|----------------|------------------------
Scope                | Local only     | Multiple locations
Support              | 4,094 VLANs    | 16 million VLANs
Distance             | Same building  | Across cities/countries
Packet Type          | Ethernet       | IP tunnel
Use Case             | Single site    | Multi-data center
Cloud Ready          | No             | Yes
VM Mobility          | Limited        | Full support
Complexity           | Simple         | Complex
Latency              | Lower          | Slightly higher


REAL WORLD EXAMPLE:
===================

Company: E-Commerce with 2 data centers

OLD SETUP (VLAN only):
- NY Data Center: VLAN 100 for database, VLAN 200 for web servers
- LA Data Center: Different VLANs (can't be same numbers)
- Devices in NY can't talk to LA!
- Need complex routing
- VM migration between DC breaks connectivity

NEW SETUP (VXLAN):
- NY Data Center: VXLAN 100 for database, VXLAN 200 for web servers
- LA Data Center: SAME VXLAN 100 and 200!
- Devices in NY CAN talk to LA!
- VM migration = connectivity stays!
- Automatic failover = network extends

Result: Seamless multi-data center network!

HSRP allows two routers to share a virtual IP address.

Virtual IP address = 192.168.1.1 (this is a fake IP, not on any router)

- Router-A is primary = all traffic goes here
- Router-B is backup = just waiting

interface GigabitEthernet0/0
ip address 192.168.1.10 255.255.255.0 (Router-A's actual IP)
standby 1 ip 192.168.1.1 (Virtual IP)
standby 1 priority 110 (High priority = active)
standby 1 preempt (Take back control if higher priority)

Configuration on Router-B:

interface GigabitEthernet0/0
ip address 192.168.1.11 255.255.255.0 (Router-B's actual IP)
standby 1 ip 192.168.1.1 (Same virtual IP)
standby 1 priority 100 (Lower priority = standby)

I tested it - shut down Router-A. What happened?

Router-A: Down
Router-B: Immediately active
Employees: No one noticed anything! Internet kept running!

One time the router had a power supply failure. It automatically restarted.
HSRP detected this, Router-B took control, then when Router-A came back up,
preemption made it take control again.

Everything was seamless! No downtime!

Verification - I ran 'show standby':

Standby Group 1
State is Active
Virtual IP is 192.168.1.1
Active router is local
Standby router is 192.168.1.11

Clear - Router-A is active, Router-B is standby.

WHAT IS PYTEST AND UNIT TESTING?
================================================================================

Sir, pytest is a Python testing framework used to test code automatically.

Unit testing is my protection before going to production!

Instead of manually checking output, we write test cases and use "assert"
to verify whether the function is giving correct result or not.

================================================================================
SIMPLE EXAMPLE
================================================================================

Suppose I have a function:

    def add(a, b):
        return a + b

Now I write a test case using pytest:

    def test_add():
        assert add(2, 3) == 5

Here, assert compares:
- Expected value = 5
- Actual value = add(2, 3)

Result:
- If both match → test passes ✓
- If not → test fails and pytest shows error with expected vs actual values ✗

test_*.py

def add(a, b):
    return a + b

def test_add():
    assert add(2, 3) == 5

WHAT IS ASSERT KEYWORD?
================================================================================

Assert keyword checks if a condition is True:

    assert condition

Common assertions:

    # Equality
    assert add(2, 3) == 5           # Check if equal

    # Not equal
    assert add(2, 3) != 6           # Check if not equal

    # Greater than
    assert 10 > 5                   # Check if greater

    # Less than
    assert 3 < 5                    # Check if less

    # In string/list
    assert "outside" in output      # Check if substring exists

    # None check
    assert result is None           # Check if None

    # Boolean
    assert True                     # Check if True

If assertion is True → test passes ✓
If assertion is False → test fails ✗ with error message

    def test_add():

TEST DRIVEN DEVELOPMENT (TDD)
================================================================================

Now I follow TDD - Test Driven Development

Traditional approach:
1. Write code
2. Write tests
3. Hope code passes tests

TDD approach:
1. Write tests FIRST (for a feature that doesn't exist yet)
2. Run tests (they FAIL because code doesn't exist)
3. Write code to make tests PASS
4. All done!

Benefits:
✓ Forces you to think about requirements first
✓ Tests are always aligned with code
✓ No untested code
✓ Better code design

Example with TDD:

    # Step 1: Write test FIRST (function doesn't exist yet)
    def test_validate_interface_name():
        assert validate_interface_name('Ethernet0/0') == True
        assert validate_interface_name('Invalid!@#') == False
        assert validate_interface_name('') == False

    # Step 2: Run test (FAILS because function doesn't exist)
    # pytest test_interface.py
    # ERROR: validate_interface_name not defined

    # Step 3: Write function to make test PASS
    def validate_interface_name(name):
        if not name:
            return False
        if not name.replace('/', '').replace('.', '').isalnum():
            return False
        return True

    # Step 4: Run test again (PASSES)
    # pytest test_interface.py
    # ✓ 3 passed

Now code is guaranteed to work as expected!
