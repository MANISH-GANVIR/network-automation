Q2: DIFFERENCE BETWEEN NETMIKO, PARAMIKO, NAPALM
================================================================================

Answer (As you'd speak in interview):

"Definitely sir! These are three networking libraries, but each has its own
level of complexity and use case.

Paramiko - this is the lowest level. Basically it handles SSH connections. When
I manually SSH to a device and send a command, Paramiko is working in the
background. If I use Paramiko directly, I have to write a lot of code and
handle errors manually. I've used it when I needed to configure some non-standard
devices.

Netmiko - this is one layer above Paramiko. It's much more simplified. I just
tell it 'this is a Cisco IOS device' and provide credentials. Then I can
directly send commands and get the output. It supports 50+ device types. In
production, I use Netmiko 80% of the time because it's fast and simple.

NAPALM - this is very high level. It gives multi-vendor support. I can write
one piece of code and run it on different vendors - Cisco, Juniper, Arista,
Palo Alto - all work with the same code.

Let me give you a real example - if I need to configure both Cisco and Juniper
devices:

With Netmiko - I have to write separate code for Cisco and separate code for
Juniper.
With NAPALM - I write one code and it works on both devices.

Yes, NAPALM is a bit slower and more abstract - meaning I don't get direct
control. But if I need to work with diverse devices, NAPALM is the best choice.

In my VPN project, I had to support both Cisco and Palo Alto, so I used NAPALM.
The same functions worked on both devices."

Q6: DIFFERENCE BETWEEN BGP AND OSPF
================================================================================

Answer (As you'd speak in interview):

"Definitely sir! These are two routing protocols but completely different.

OSPF - this runs in my company's internal network. A single network, within
the company.

For example, suppose my office has 5 buildings in different cities. All
buildings are connected with OSPF. If any path changes, OSPF automatically
finds the best path. And it's very fast - it converges in seconds.

BGP - this is when you need to connect to another company or to the Internet.
Much more control is needed.

Real example - my company is in Delhi, head office is in New York. New York's
ISP is Comcast (AS 65001) and Delhi has Airtel (AS 65002).

With BGP setup:
1. I created a neighbor with the ISP router
2. I wrote policies - which traffic goes which way
3. I advertised my routes
4. Now communication is perfect between both locations

OSPF practical experience:

I had a Cisco router, and the configuration was very simple:

router ospf 1
network 10.0.0.0 0.255.255.255 area 0

That's it! OSPF automatically discovers neighbors and finds the best path.

BGP is more complex:

router bgp 65001
neighbor 203.0.113.1 remote-as 65002
address-family ipv4
network 192.168.0.0

Plus route maps, policies - lot of configuration.

Key difference that I feel in practice:

OSPF - simple, fast convergence, for one company
BGP - complex, slower convergence, for multiple networks, used by ISPs

Honestly, OSPF seemed easier and faster to me. But BGP is more powerful and
gives you control.

In production, we use both:
- Internal (company offices): OSPF
- External (Internet): BGP"

Q7: WHAT IS VLAN?
================================================================================

Answer (As you'd speak in interview):

"Sir, VLAN is basically logical division of a network.

Simple analogy - suppose a building has 4 floors. Physical cables from all
floors go to the switch. Create VLANs and you get:

Floor 1 = VLAN 100
Floor 2 = VLAN 200
Floor 3 = VLAN 300
Floor 4 = VLAN 400

Now Floor 1's broadcast traffic will not reach Floor 2! Completely isolated.

I used VLANs a lot in production.

Security example - I created VLAN 100 for the HR department and VLAN 200 for
the IT department. Now HR's sensitive salary data is not visible to IT! Good
security!

Performance also improves. If everything was in one VLAN, broadcast traffic
affects everyone. Separate VLANs limit broadcast traffic.

Flexibility - an employee transferred from Floor 1 to Floor 2. In the switch,
I just changed the port from VLAN 100 to VLAN 200. Never had to unplug or
replug! Beautiful!

In my automation project, I wrote code to create VLANs automatically!

To assign VLAN to an interface:

interface Ethernet1/1
switchport access vlan 100

Now this port is in VLAN 100.

I had a practical issue to solve - an employee accidentally got access to the
production server because of VLAN configuration. Risky!

I moved the employee's laptop from VLAN 100 (production) to VLAN 200
(non-production). Now they cannot access production data.

VLAN naming convention is important - the name should tell you what the VLAN
is for."

Q8: WHAT IS HSRP?
================================================================================

Answer (As you'd speak in interview):

"Sir, HSRP saved my company once!

Scenario - my company had one main router, and all network traffic went through
it. One day this router went down and the entire network crashed!

My boss said, 'Single point of failure? How is this possible?'

That's when I realized I needed redundancy. HSRP solved this problem.

HSRP allows two routers to share a virtual IP address.

Example - I have Router-A and Router-B. I connect them with HSRP:

Virtual IP address = 192.168.1.1 (this is a fake IP, not on any router)

I tell all employees: use gateway IP 192.168.1.1

What happens:
- Router-A is primary = all traffic goes here
- Router-B is backup = just waiting
- If Router-A goes down, Router-B instantly claims that IP address in less
  than 1 second!

Configuration on Router-A:

interface GigabitEthernet0/0
ip address 192.168.1.10 255.255.255.0 (Router-A's actual IP)
standby 1 ip 192.168.1.1 (Virtual IP)
standby 1 priority 110 (High priority = active)
standby 1 preempt (Take back control if higher priority)

Configuration on Router-B:

interface GigabitEthernet0/0
ip address 192.168.1.11 255.255.255.0 (Router-B's actual IP)
standby 1 ip 192.168.1.1 (Same virtual IP)
standby 1 priority 100 (Lower priority = standby)

I tested it - shut down Router-A. What happened?

Router-A: Down
Router-B: Immediately active
Employees: No one noticed anything! Internet kept running!

One time the router had a power supply failure. It automatically restarted.
HSRP detected this, Router-B took control, then when Router-A came back up,
preemption made it take control again.

Everything was seamless! No downtime!

Verification - I ran 'show standby':

Standby Group 1
State is Active
Virtual IP is 192.168.1.1
Active router is local
Standby router is 192.168.1.11

Clear - Router-A is active, Router-B is standby.

Honestly, HSRP saved my company multiple times. You understand its importance
when you have an actual outage!"

================================================================================

- Switch-A
- Switch-B

vPC makes two physical switches behave like one logical switch!

Architecture:
- Switch-A and Switch-B connected
- Peer link = dedicated link between them (high bandwidth)
- Servers connected to both switches

Benefits:

Redundancy:
- One switch goes down = other switch takes over
- I tested it - shut down Switch-A = servers kept working
- Switch-B immediately started serving the traffic

Load balancing:
- Traffic is 50-50 between both switches
- Before: Switch-A overloaded, Switch-B idle
- Now: 50-50 bandwidth distribution

No STP blocking:
- Spanning tree port blocking doesn't happen
- Before: 50% bandwidth wasted because of STP blocking
- Now: 100% utilization!

Real incident - Switch-A's fan failed and it automatically shut down due to
overheating.

What vPC did:
- Switch-B immediately took over server traffic
- No servers got disconnected
- No customer complaints
- Team had 2 hours to replace the switch

If vPC wasn't there:
- Complete data center outage!
- All customers disconnected!
- Emergency response needed!

Verification showed both switches were perfectly synchronized!

Complexity I had to handle:

Peer link - needs dedicated high bandwidth link (40G+)
Keepalive - must be on separate network (management network)
Config consistency - both switches need exactly same configuration

vPC seemed advanced at first, but seeing how powerful it is in production, I
understood - it's almost mandatory in data centers!"

Q13: WHAT IS TRY-EXCEPT IN PYTHON?
================================================================================

Answer (As you'd speak in interview):

"Sir, try-except is basically crash protection!

Scenario - when you run a script and one line fails, the entire script stops!
Very bad!

With try-except, you don't lose the script. Errors get handled and the script
continues.

Real example when this was a lifesaver:

My script configured 50 devices. 49 succeeded, 1 device's password had changed
- authentication failed.

WITHOUT try-except (before):

The script would:
1. Configure device 1 successfully
2. Configure device 2 successfully
3. ... continues ...
4. Configure device 49 successfully
5. Try to configure device 50 - CRASH! Authentication failed!
6. ENTIRE SCRIPT STOPPED!

Boss got report: '49/50 success' - but the script crashed, bad reputation!

WITH try-except:

for device in devices:
    try:
        net_connect = ConnectHandler(**device, timeout=10)
        net_connect.send_command('show version')
        print(f'✅ {device[host]} - SUCCESS')

    except Exception as e:
        print(f'❌ {device[host]} - FAILED: {str(e)}')
        continue

Output:
✅ Device 1 - SUCCESS
✅ Device 2 - SUCCESS
... continues ...
✅ Device 49 - SUCCESS
❌ Device 50 - FAILED: Authentication failed
✅ Script completed successfully!

Professional and smart!

Handling different exceptions:

from netmiko.ssh_exception import NetMikoTimeoutException, NetMikoAuthenticationException

try:
    net_connect = ConnectHandler(**device)
    output = net_connect.send_command('show version')

except NetMikoTimeoutException:
    print(f'Device not reachable - Check connectivity')

except NetMikoAuthenticationException:
    print(f'Wrong credentials - Check username/password')

except ValueError:
    print(f'Invalid parameters')

except Exception as e:
    print(f'Unknown error: {str(e)}')

Else and finally blocks:

try:
    net_connect = ConnectHandler(**device)
    output = net_connect.send_command('show version')

except Exception as e:
    print(f'Error: {str(e)}')

else:
    print('✅ SUCCESS - Command executed perfectly')

finally:
    print('Cleaning up: Closing connection')
    if net_connect:
        net_connect.disconnect()

Finally is important - it runs every time, success or failure!

Even if try block has return statement, finally will execute. Cleanup code
always runs!

Real production code I wrote handles all these cases properly.

Benefits:

✅ Script doesn't crash
✅ Error messages are clear
✅ Logging makes debugging easy
✅ Production stability improves

When my production script crashed without try-except the first time, that's
when I understood how important this is!"

Q14: WHAT IS UNIT TESTING?
================================================================================

Answer (As you'd speak in interview):

"Sir, unit testing is my protection before going to production!

Scenario - I wrote a function called validate_vlan_config()

This function is critical to the whole script. If it works incorrectly, the
entire system fails!

So I needed to ensure the function works 100% correctly. That's where unit
tests come in!

Real function:

def validate_vlan_config(vlan_id, vlan_name):
    if not vlan_id or not vlan_name:
        raise ValueError('VLAN ID and name required')

    if vlan_id < 1 or vlan_id > 4094:
        return False

    if len(vlan_name) > 32:
        return False

    return True

Now I need to test - does this function work perfectly?

WITHOUT unit testing (manual approach):

Just run it a couple times:
result = validate_vlan_config(100, 'Production')
print(result)  # True

result = validate_vlan_config(5000, 'BadVlan')
print(result)  # False

Very limited! Only tested 2 cases.

WITH unit testing (using pytest):

import pytest

class TestVLANValidation:

    def test_valid_vlan(self):
        result = validate_vlan_config(100, 'Production')
        assert result == True

    def test_invalid_vlan_range_high(self):
        result = validate_vlan_config(5000, 'Invalid')
        assert result == False

    def test_invalid_vlan_range_low(self):
        result = validate_vlan_config(0, 'Invalid')
        assert result == False

    def test_vlan_name_too_long(self):
        long_name = 'A' * 50
        result = validate_vlan_config(100, long_name)
        assert result == False

    def test_vlan_name_exactly_32_chars(self):
        name = 'A' * 32
        result = validate_vlan_config(100, name)
        assert result == True

    def test_missing_vlan_id(self):
        with pytest.raises(ValueError):
            validate_vlan_config(None, 'Production')

    def test_missing_vlan_name(self):
        with pytest.raises(ValueError):
            validate_vlan_config(100, None)

    def test_boundary_vlan_1(self):
        result = validate_vlan_config(1, 'DefaultVLAN')
        assert result == True

    def test_boundary_vlan_4094(self):
        result = validate_vlan_config(4094, 'MaxVLAN')
        assert result == True

Running it:

pytest test_vlan.py -v

Output:

test_vlan.py::TestVLANValidation::test_invalid_vlan_range_high PASSED
test_vlan.py::TestVLANValidation::test_invalid_vlan_range_low PASSED
test_vlan.py::TestVLANValidation::test_vlan_name_too_long PASSED
test_vlan.py::TestVLANValidation::test_vlan_name_exactly_32_chars PASSED

Mocking (when external dependencies exist):

When you connect to real devices, production data gets affected. So you use

show ip access-list CRYPTO-ACL

10.1.1.4         Active ← PROBLEM!

3 neighbors were failing! BGP was constantly trying to connect them = CPU

STEP 5 - Check memory

show memory

Both CPU and memory had issues!

SOLUTION that I implemented:

1. Restart the failing neighbor:

clear ip bgp 10.1.1.3

Connection restored!

2. Reduce BGP update frequency:

router bgp 65001
timers bgp 60 180 (was 10/30 before)

CPU dropped to 45%!

3. Optimize routing table:

aggregate-address 10.0.0.0 255.0.0.0

Routes reduced to 25,000

4. Monitor after fix:

CPU is now 35% (normal!)

Recommendations based on findings:

IF BGP neighbors failing:
- Check neighbor IP reachability
- Check authentication
- Clear the neighbor: clear ip bgp <neighbor>
- Increase timers to reduce chatter

IF routes very high:
- Aggregate routes
- Use prefix lists
- Consider design change

IF still high:
- Restart device (during maintenance window)
- Upgrade to higher capacity device
- Load balance across multiple devices

Honest assessment:

High CPU is usually a routing protocol issue, not hardware!

Troubleshooting path:
1. Check overall CPU
2. Find top process
3. Debug that specific process
4. Fix it

Device restart should be the last option!"
